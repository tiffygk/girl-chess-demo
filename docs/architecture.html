Girl Chess: architecture

A personal chess tutor I built for myself. I play an engine opponent called mallow; cookie, the coach, answers my questions during and after the game. One part of the system is not deterministic; everything else is arithmetic over stored facts.
The model is never asked to compute chess. It puts facts the code already computed into words, and checks compare what it says against those facts.
Each wrong answer I traced came from a fact the coach was not handed or a check that did not run. None was fixed by a bigger model.

01

The determinism boundary

One part of the entire system is not deterministic. Everything else is arithmetic over stored facts.
chess.js decides legality.
Stockfish decides truth: how much better a position is, whether a forced mate exists, and the best line.
Maia decides what a human of a given rating would actually play.
The annotator decides what mattered: verdict tiers, turning points, conversion failures, game phase.
Claude only puts it into words.

From the spec: code computes every chess fact, award and schedule; the model only phrases them.

Four texts reach me. Code writes two of them from templates filled with stored facts: the hint ladder under the board and the debrief after the game. The coach writes the other two: its chat replies and the one-line note under the hint ladder. Those are the only sentences a model composes.

LESSON

If the debrief says something false, the bug is in my code, not in a model: the annotator never calls one, so it cannot make up a fact. Where the coach writes, its words are checked before I see them (§08).

02

Two engines: Stockfish for truth, Maia for human play

Stockfish scores positions. Maia plays mallow the way a person at my chosen rating would. They run side by side, neither reads the other, and each sits behind its own interface, so either can be swapped.

From the spec: opponents that play human-like at every level up to Maia's 1900 cap.

Stockfish

Stockfish searches ahead through the tree of possible moves and scores each position with a small neural network trained on millions of positions. It plays the strongest chess it can find and has no notion of what a person would do. Here it is the source of truth for the judge, the hints and the debrief.

Maia

lc0 plays the opponent using Maia weights, a trained weights file rather than a separate engine, across nine bands from 1100 to 1900. lc0 learned chess by playing itself. Maia uses the same kind of network, trained on human games from Lichess instead, one model per rating band, so it predicts the move a player at that rating would make, mistakes included. It runs with search off, one node per move.

Two settings that cost debugging

At lc0's default temperature of 0, Maia always plays its single most likely move, which plays stronger than its band; at 1.0 it samples moves the way players at that rating do. And every query starts with a new-game reset, because a warmed engine could otherwise return the same move call after call.

04

One coach interface, four backends

The coach talks to one interface, and four backends sit behind it: Claude through the Anthropic Agent SDK by default, the Claude command-line tool, a local model through Ollama, and canned replies.

From the spec: the game never depends on a subscription to run; a local model sits behind the same interface.

I built the interface before there was a speed problem. By Jul 21, 2026, 13 of 14 live nudges had missed their 15-second budget on the Claude command-line tool, because starting a process ate most of each call. The fix, the same day, was another backend behind the same interface, Claude through the Anthropic Agent SDK, which keeps one process warm; nothing downstream changed. Every addition since has been an optional parameter, so the other backends needed no edits. The Agent SDK backend is the only one I have optimized: streaming, prompt caching and the thinking setting exist only there.

05

Two coach surfaces, one chess brain

The worst bug here was plumbing, not the model. Two surfaces search the same position: the judge, on every move I consider, and the hint, only when I ask (their search times are in §02).

From the spec: a chat answer is grounded in engine facts, and thumbs-down captures why it missed.

TimeGame 167, move 19, 2026-08-02 -- every row from the database
11:18The hint engine found a forced mate, verified it, and showed it to me on screen.
11:21I asked the coach about it. It timed out and served a canned template.
11:22I asked again. It replied: "no mate line for this position in the facts i've got."

"The hint said that there's a forced mate that's available if I move my knight to G5. When I tried to ask the coach about it, the coach couldn't figure it out and gave a timed-out answer. Now, even after feeding it to the coach and telling it to check the chess facts from stockfish, the coach is claiming that the chess brain has not found a forced mate, but I know that it has."

my playtest note, 2026-08-02

The cause? The hint computed the mate, used the score to pick which piece to point at, then threw it away at the return. The mate distance was never carried. The coach's facts had ten categories and zero mentions of mate. The mate checker's set of true mate distances was empty, so nothing even blocked a mate claim. The model correctly refused to invent one.

LESSON

The coach and the hint answer from one search. The hint's verified findings are kept per position and reach the coach only on an exact position match. For a position the hint has not searched, or a move I name in chat but have not played, the coach runs that same verified search first.

06

Routing: this board, or chess in general

Before any model call, code decides: this position, or chess in general?

From the spec: when I do not understand why a move was wrong, I ask in plain English and get an answer at my level.

It began as a thumbs-down: "will only answer about moves i already did, not general chess questions for strategy next game." The refusal came from a line in the prompt, not a check, so the decision moved into code, before the call. Letting the model route itself was the failure I had already hit.

Board is the default because 38 of the 65 board questions I asked carry no signal a router can detect: "is this ok", "should i take it", a bare "yes". Sent to general, each would be answered without the position.

When a hint is showing, an "ask about this" button opens the chat pinned to that hint. That pin is what the first question in the flowchart checks, and a yes goes straight to board.

Both routes think at the same low setting; they differ in what the coach is handed and what it may draw on.

TESTED ON MY REAL MESSAGES

On Aug 3, 2026, before merging, a read-only tool replayed the old and new routing over 102 of my real messages. Zero board questions flipped to general.

07

Supplementing the coach with facts and checks

An iterative process. Each time the coach or the game review got something wrong, I handed the coach a fact the code already held, or added a check on what it said. The timeline starts in July, about when I launched the game.

DateWhat it saidMissing fact or check
Jul 21Described my own pending move as mallow's, and told me I'd win my own queen for free.Whose turn it is
Jul 22Said my pawn on e4 did not guard f5. It does. That exact trade happened a few moves later.The attacked-and-defended map
Jul 227.5% of its statements about where pieces sat were false. Nothing checked them.Occupancy, and a checker
Sep 21Threw out 14 true answers in one game, because the check compared where a piece would stand after the move to the board from before it.The check reads every board the coach was shown, not only the current one

LESSON

None of the July additions needed a bigger model. They needed facts the code already had. With them, placement errors fell from 7.5% to zero and explanation latency from 13-15 seconds to about 4, on the small model and the large one alike. In September the gap was in the checks: one compared answers to the wrong board, and one kind of claim had no check. Both are fixed: after a move, true answers wrongly rejected went from 65 of 144 to 0.

08

Regression checks: what the coach can't say

Nine checks, and which run depends on where the coach writes: board chat, general strategy chat, or the note under the hint ladder.

From the spec's ship gates: zero invented moves; a failed fact-check pauses the coach, never the game.

Which checks run where

The note under the hint ladder is about one thing: the move I have picked up and am deciding whether to confirm. So its square list is strict: every square it names must come from its facts, the threat and the recommended move, and it cannot drift to pieces outside that move. Chat is meant to range wider, into what happens next and what else to consider, so it runs the placement check instead of a closed list.

LESSON

So adding a check is free. The cost is the retry, which is why the correction for mallow's move quality fixes the wording in place instead of asking for one. A check that rejects true answers costs the same way: in one September game, 14 of the placement check's 16 rejections threw out true answers (§09).

09

Proving a fix on past games

I do not wait for new games to find out whether a fix worked. A fix runs against every position already stored, before and after the change, and then I break it on purpose to prove the harness can tell the difference.

From the spec: a red flag is something to fix, not a feature to cut, and diagnosis starts from my thumbs-down notes and the traces.

In game 198 the check on where pieces stand rejected 16 coach answers. 14 were true statements about the position after the move being explained; the check had compared them to the board before it. The easy fix was to delete the check. I kept it and taught it which boards the coach was talking about, and it still catches the 2 answers that were wrong.

A check only ever seen passing proves nothing. So I broke the fix on purpose: pulling the move lines back out brought the after-move rejections straight back, and restoring them cleared them again. Four such breaks ran, each built to move one named cell of the results and nothing else.

Equal mates count as the best move

The same method proved a second fix. In game 198 my move mated as fast as the engine's stored best move, and the review still marked it as a miss, because it compared the two by name rather than by how fast they mate. The fix treats an equally fast mate as the best move everywhere the review judges a move.

WHAT IT CANNOT CATCH YET

The placement check accepts a claim that is true on any board the coach was shown, up to four moves down a line. A claim about the current board that only becomes true a few moves later would pass, and the "false statements caught" figures above are measured against that rule. Nothing yet measures how often the coach writes one in play.

10

How we set thinking and effort

Two independent controls, not one parameter. One turns adaptive thinking off. The other caps it at low and leaves it on.

Latency by arm

Fallback by difficulty

So why low? Difficulty, not the average. On the hardest bucket it beats both. It beats disabled in every bucket at a speed cost inside the noise, and beats default on tactical questions while running 2.3x faster on a fifth of the tokens. A blinded human read of 26 questions, columns randomized and the key held separately, gave the bounded arms 18 of 25 non-tie picks.

11

Finding that root cause took four passes

The first three passes each found a cause, shipped a fix, watched the median improve, and filed the rest under model variance. The fourth pass zoomed out and ran a root cause analysis, a method from total quality management: it accounted for every second of one slow call, which surfaced what the first three passes were not measuring. The same investigation used a fishbone diagram to sort a failure with several causes, where a forced mate the hint knew about never reached the chat.

PassDiagnosisRight?
Jul 21Process startup, not thinking timeYes, and so was the fix
Jul 27Budgets are too tightA mitigation, not a diagnosis
Aug 1Stale served code, starved retry cap, prompt sizeTwo right. The third was a confound
Aug 2Unbounded adaptive thinking, 1,500-4,500 invisible tokensNamed, reproduced, toggled

Anatomy of one 20.3-second call

It hid because thinking streams with empty text by default: no log, trace or stream ever showed a thinking token. Both tells were arithmetic and sat in every call: the gap between the first token and the whole wait, and billed output tokens far larger than the visible answer.

LESSON

A fix that measurably helps is the most dangerous stopping point. It validates the pass without validating the diagnosis. Zoom out and name the confounders. Build an eval for what was not being measured, so the cause that matters shows up. The obvious fix, prompt size, was already measured and would only have been a band-aid.
